# Группировка связанных событий на пресете «Авторизация»

**Дата:** 2026-07-12
**Статус:** утверждено

## Проблема

Одно реальное действие пользователя (например, разблокировка/подтверждение UAC) генерирует
несколько «сырых» записей в журнале Security почти в одну секунду. Разобранный пример
(12.07.2026 08:57:15.247, пользователь `iNB`):

| Событие | Что это |
|---|---|
| 4648 | Попытка входа с явным указанием учётных данных (инициатор, `svchost.exe`) |
| 4624 (LogonId `0x19c96ab`) | Сеанс входа #1 — обычный токен |
| 4624 (LogonId `0x19c96e4`) | Сеанс входа #2 — повышенный (admin) токен |
| 4672 | Спецпривилегии — назначены только сеансу #2 |
| 4634 ×2 | Оба сеанса сразу же закрыты (это была проверка учётных данных, не постоянная сессия) |

Это стандартное поведение Windows для админ-аккаунтов с включённым UAC (linked/split-token
logon), не дублирование на нашей стороне — у записей разные `TargetLogonId`, то есть с точки
зрения ОС это действительно разные сеансы. Тем не менее пользователю неудобно видеть 6 строк
там, где по сути произошло одно событие «вошёл».

## Область действия

Группировка — **чисто отображение, только на frontend**, только на пресете «Авторизация»
(`presetKey === 'auth'`). Backend, API-контракт (`EventLogQueryParams`/`EventLogQueryResult`),
`maxRecords`/`truncated`-семантика и счётчик `data.entries.length` в подзаголовке страницы —
**не меняются**. Группировка применяется к уже отфильтрованному (в т.ч. переключателем «Только
пользователи») массиву `data.entries` непосредственно перед передачей в `dataSource` таблицы.

## Критерий группировки

Идём по `data.entries` в том порядке, в котором он приходит с бэкенда (текущий рендер-порядок,
переопределять сортировку не нужно). Группируем **подряд идущие** записи, у которых:
- совпадает `user` (точное совпадение строки, включая `undefined`/`null` — такие тоже могут
  группироваться друг с другом, если идут подряд);
- разрыв по времени (`timeCreated`) между текущей записью и **предыдущей** записью того же
  прогона группы ≤ 2 секунд.

Если следующая запись — другой пользователь или разрыв > 2 сек, группа завершается. Запись,
которая не сгруппировалась ни с кем (группа размера 1), рендерится и ведёт себя ровно как
сейчас — без стрелки разворота, клик по строке открывает `Modal` с деталями, как и раньше.

## Синтезированный заголовок группы

Для группы размера ≥ 2 вычисляем заголовок по приоритету присутствующих `eventId`
(первое совпадение побеждает):

1. Есть `4625` → **«Неудачный вход»** (тег `red`)
2. Есть `4624` **и** `4672` → **«Вошёл (admin)»** (тег `green`)
3. Есть `4624` (без `4672`) → **«Вошёл»** (тег `green`)
4. Есть `4634` или `4647`, но нет `4624` → **«Вышел»** (тег `blue`)
5. Иначе → **«N событий»** (тег `default`) — страховка на нераспознанные сочетания
   (например, только события управления учётками 4720/4738/… без логон-событий рядом)

## Таблица: рендер строки-группы

Для строки-группы (не для развёрнутых дочерних строк — там рендер каждой записи не меняется):
- **Время** — `timeCreated` **первой** (самой ранней по порядку) записи группы.
- **Уровень** — синтезированный тег из правила выше вместо обычного `LEVEL_COLORS`-тега.
- **Источник** — прочерк (`—`).
- **ID события** — бейдж вида `«N событий»` вместо одного `eventId`.
- **Пользователь** — как обычно (`user` группы, они все совпадают по определению).
- **Сообщение** — прочерк (`—`).

Разворачивание — встроенный `expandable` пропс antd `Table` (`expandedRowRender`), стрелка
слева от строки. Внутри — список исходных записей группы (время, `eventId`, `levelDisplayName`,
`message`), с возможностью клика по каждой для открытия того же `Modal` с полными деталями,
что и сейчас для одиночных записей. Клик по самой строке-группе (не по дочерним) переключает
`expanded`/`collapsed` (`expandRowByClick: true` в `expandable`), а не открывает `Modal` — у
синтетической строки нет единого «одного события» для показа в деталях.

## Реализация

Никаких изменений в backend/API. В `EventLogs.tsx`:
- Новая чистая функция `groupAuthEvents(entries: EventLogEntryDto[]): AuthEventGroup[]`
  (или аналогичное имя), вызываемая только когда `isAuthPreset` — для остальных пресетов
  `dataSource` остаётся `data?.entries ?? []` без изменений.
- Тип строки таблицы становится объединением: одиночная запись (`EventLogEntryDto`) или
  группа (`{ isGroup: true; key: string; entries: EventLogEntryDto[]; timeCreated: string;
  user?: string; summary: {label: string; color: string} }`), при этом группа размера 1 не
  создаётся — в неё превращаются только настоящие кластеры (≥ 2 записи).
- Колонки таблицы получают условный рендер: если `record` — группа, показываем синтетические
  значения (см. выше), иначе — текущее поведение без изменений.

## Тестирование

Поскольку логика чистая (вход — массив записей, выход — массив групп), она тестируется без
рендеринга компонента. Проект уже использует xUnit для backend; на фронтенде выделенного
тест-раннера сейчас нет (в `package.json` нет `test`-скрипта, и в `src/frontend` нет тестов) —
проверка вручную: открыть пресет «Авторизация», убедиться что кластер `08:57:15` (6 событий)
схлопывается в одну строку «Вошёл (admin)» с корректным разворачиванием, а изолированные
события (например, одиночный `4625`) остаются как есть.

## Вне рамок

- Изменение backend/API-контракта.
- Точная (по `LogonId`) корреляция вместо временной эвристики.
- Группировка на других пресетах.
- Настройка длины временного окна (2 сек — фиксированное значение).
